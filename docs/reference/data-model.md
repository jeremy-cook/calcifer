# Data model & RPC reference

Descriptive reference for the shapes the system actually uses. The *why* behind these
choices lives in [`../adr/`](../adr/); this file is the what.

---

## Entities

Authored in `proto/calcifer/v1/entities.proto`; TS generated into `calcifer/gen/ts/`
and aliased as `@calcifer/proto`; Rust generated by `tonic-build` at compile time.

```proto
message EntityRef     { string id = 1; string structure_type = 2; }
message EntityRefList { repeated EntityRef refs = 1; }
message RichTextRef   { string entity_id = 1; string property_id = 2; }  // a RichText's address

message PropertyValue {
  oneof value {
    string text = 1;
    double number = 2;
    string date = 3;            // calendar day "yyyy-MM-dd"; not an instant
    string select = 4;          // option key; allowed set defined on the Structure
    EntityRef relation = 5;
    EntityRefList relations = 7; // multi-target relation; server derives links from it
  }
}

// Output only; clients write through PutRichText.
message RichText {
  RichTextRef ref = 1;
  string doc = 2;               // TipTap JSON; schema in richtext-doc.md
  google.protobuf.Timestamp updated_at = 3;
}

message LinkRef {
  string id = 1;                      // relationship uuid
  EntityRef target = 2;
  string source_property_id = 3;      // originating property (e.g. 'content')
  google.protobuf.Timestamp created_at = 4;
}

// Output only: no request carries an Entity (ADR 8).
message Entity {
  string id = 1;                              // output only
  string structure_type = 2;    // 'Note' | 'Tag' | 'DailyNote' | ...
  string name = 3;
  map<string, PropertyValue> properties = 4;  // keyed by property id
  repeated LinkRef links = 5;   // output only; outgoing; backlinks are derived
  google.protobuf.Timestamp created_at = 6;   // output only
  google.protobuf.Timestamp updated_at = 7;   // output only
  repeated string referenced_dates = 8;       // output only
  repeated string facets = 9;   // output only; attached facet ids, in registry order
}
```

`Entity` is only ever returned. Clients write through intent-shaped RPCs (`CreateEntity`,
`RenameEntity`, `SetEntityProperty`, `DeleteEntity`, `ResolveEntity`, `AttachFacet`,
`DetachFacet`, `AddRelationTarget`, `RemoveRelationTarget`, `AddRelationship`,
`RemoveRelationship`) and the server owns the id, links, referenced dates and timestamps
([ADR 8](../adr/0008-server-builds-entities.md)).

`facets` lists the facets attached to the entity (see Facets under Structures), and
their values are in `properties` under the facet's namespaced ids (`todo.status`). Which
facets an entity has lives in its own table; deleting the entity cascades:

```sql
CREATE TABLE entity_facets (
  entity_id TEXT NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
  facet     TEXT NOT NULL,   -- 'todo'
  PRIMARY KEY (entity_id, facet)
);
```

Direct relationships ([ADR 12](../adr/0012-direct-relationships.md)) are one-way
associations from an entity to another, one row each, in their own table. Deleting either
end cascades:

```sql
CREATE TABLE relationships (
  entity_id  TEXT NOT NULL REFERENCES entities(id) ON DELETE CASCADE,  -- the source
  target_id  TEXT NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
  created_at INTEGER NOT NULL,
  PRIMARY KEY (entity_id, target_id)
);
CREATE INDEX relationships_target ON relationships(target_id);
```

A relationship is a row and not a property value: it never appears in `Entity.properties`
and `SetEntityProperty` can't write it. It reaches clients as a `LinkRef` in `Entity.links`
whose `source_property_id` is the reserved scope `@related` (see Graph derivation).
`AddRelationship` and `RemoveRelationship` write it, one target at a time.

Rich text lives in a parallel slice, so list and metadata reads never pull document
bodies. A document is addressed by declared property: a `RichTextRef` is the entity's
id plus one of the property ids its structure declares with `PROPERTY_KIND_RICHTEXT`
(today `content` on Note and DailyNote). A rich-text property has no
`PropertyValue` and never appears in `Entity.properties`; clients build the ref from
the entity id and the registry, and every declared rich-text property has a document
to read (empty until first saved).

A document is TipTap JSON that the server parses on every save. The node types and
attributes it reads (`mention`, `hashtag`, `dateChip` and text) and what it derives from
each are specified in [`richtext-doc.md`](richtext-doc.md).

Field formats: a `date` value, `ResolveEntityRequest.date` and every
`referenced_dates` entry are ISO calendar days, `yyyy-MM-dd`. The server checks them:
`CreateEntity`, `ResolveEntity` and `SetEntityProperty` return `INVALID_ARGUMENT` for a
`date` value that isn't a real day in that canonical form (`2026-13-45`, `2026-2-3`,
`June 13`, `""`); clear a date by removing the property. A date chip with a bad `date` is skipped (see
[`richtext-doc.md`](richtext-doc.md)). In a relation value the
server reads only each `EntityRef`'s `id`; `structure_type` may be empty.

## Structures

The registry is authored in exactly one place, the static `STRUCTURES` table in
`server/src/structures.rs` ([ADR 7](../adr/0007-server-owned-structure-registry.md)),
and served by `StructureService.ListStructures`. Today: `Note`, `Tag`, `DailyNote`, plus
the `todo` facet (`FACETS`, see Facets below).
Proto defines only its shape, in `proto/calcifer/v1/structures.proto`:

```proto
enum PropertyKind {
  PROPERTY_KIND_UNSPECIFIED = 0;
  PROPERTY_KIND_RICHTEXT = 1;  PROPERTY_KIND_TEXT = 2;     PROPERTY_KIND_NUMBER = 3;
  PROPERTY_KIND_DATE = 4;      PROPERTY_KIND_SELECT = 5;   PROPERTY_KIND_RELATION = 6;
  PROPERTY_KIND_RELATIONS = 7;
}

message SelectOption { string key = 1; string label = 2; }

message PropertyDef {
  string id = 1;
  PropertyKind kind = 2;
  string label = 3;                    // empty = none; clients fall back to the id
  repeated SelectOption options = 4;   // select only, in display (and rank) order
  string default_option = 5;           // select only; empty = none
  string target_structure = 6;         // relation/relations only; empty = any
}

message StructureDef {
  string type = 1;  string name = 2;  string plural = 3;
  string description = 4;              // one line, for the agent
  repeated PropertyDef properties = 5; // in display order
  bool creatable = 6;  bool mentionable = 7;  bool unique_names = 8;  bool name_editable = 9;
  repeated string facets = 10;         // facet ids this structure accepts, e.g. 'todo'
  repeated string relates_to = 11;     // structure types its entities may hold relationships to (ADR 12); empty = none
}

message FacetDef {
  string id = 1;                       // 'todo'
  string name = 2;                     // 'To-do'
  string plural = 3;                   // 'To-dos'
  string description = 4;              // one line, for the agent
  repeated PropertyDef properties = 5; // full namespaced ids: 'todo.status'; in display order
}
```

| Flag | Meaning |
|---|---|
| `mentionable` | Whether bare `@` autocomplete includes this Structure. `false` where the Structure has dedicated UI — `#` for Tags, the calendar for DailyNote. |
| `creatable` | Whether the sidebar "+ New" menu (and create-on-miss in `@Structure/` mentions) offers it. Enforced: `CreateEntity`, and `ResolveEntity` by name with `create_if_missing`, of a non-creatable structure is `FAILED_PRECONDITION`; a DailyNote is made by `ResolveEntity` with a date. |
| `unique_names` | Whether the case-insensitive name *is* the identity. `true` for `Tag`. Not authored: derived from the structure declaring a `name` key (see Natural keys below), and enforced by `entity_keys` (`ALREADY_EXISTS`). Other names can repeat; see `ResolveEntity` for which one a name lookup returns. |
| `name_editable` | Renders the entity title as an input vs a read-only heading. `false` for `DailyNote`. Enforced: `RenameEntity` of a structure with `name_editable: false` is `FAILED_PRECONDITION`. |
| `facets` | The facets an entity of this structure can have attached. `["todo"]` for `Note`, empty for the others. Enforced: attaching any other facet is `FAILED_PRECONDITION`. |
| `relates_to` | The structures an entity of this one may hold direct relationships to ([ADR 12](../adr/0012-direct-relationships.md)). `["Note"]` for `Note`, empty for the others. Enforced by `AddRelationship` only: an empty list is `FAILED_PRECONDITION`, a target of a structure not in the list is `INVALID_ARGUMENT`. It never limits content: a document can mention anything, and every mention is still a link. |

The server derives what its write paths need from the same table: `richtext_properties`
(which property ids `RichTextService` addresses), `select_defaults` (what `new_entity`
in `services/entity/construct.rs` puts on an entity `CreateEntity` or `ResolveEntity` creates),
`relation_properties`
(what link sync clears), and `property(type, id)` for single-definition lookups. For
facets: `facet(id)`, `facet_of_property(id)` (the facet whose namespace an id is in),
`facet_select_defaults` and `facet_relation_properties`; `property_for(type, facets,
id)` looks a definition up in the structure, then in the attached facets.

**Natural keys** ([ADR 10](../adr/0010-natural-keys-declared-by-the-registry.md)). A
`StructureDef` declares `keys`: values that identify an entity besides its id. Each
`KeyDef` has a `key` and a source, the entity's name (`KeySource::Name`, trimmed and
lowercased with Unicode folding) or a property (`KeySource::Property(id)`, used as
stored). `Tag` declares `name` from its name; `DailyNote` declares `date` from its
`date` property. The values live in one table:

```sql
CREATE TABLE entity_keys (
  structure_type TEXT NOT NULL,
  key            TEXT NOT NULL,   -- 'date', 'name'
  value          TEXT NOT NULL,   -- canonical: '2026-10-10', 'reading'
  entity_id      TEXT NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
  PRIMARY KEY (structure_type, key, value),
  UNIQUE (entity_id, key)
);
```

The primary key gives a key value to at most one entity of a structure. Create and
Resolve write every declared key, `RenameEntity` the name keys and `SetEntityProperty`
the keys sourced from that property, each in the write's transaction; clearing the
property removes the row, and deleting the entity cascades. A taken value is
`ALREADY_EXISTS`: `a DailyNote for <date> already exists`, or `a Tag named "<name>"
already exists` with the name as given. Resolve looks keys up in the same table with
the same folding. The table enforces identity only; values are still checked as
described below.
`CreateEntity`, `ResolveEntity` and `SetEntityProperty` check property values against it and return
`InvalidArgument` for a value on a property the structure doesn't declare
(`Note.mood isn't a declared property`; a facet's only while it's attached), any value on
a declared rich-text property (it takes none), a value whose case isn't the declared
property's `PropertyKind`, a select key that isn't one of the property's options, or a
`date` value that isn't an ISO day. A new property is an edit to `structures.rs` and a
server restart, not a write. Clearing is always allowed, so a value stored before
undeclared ids were refused (I-79) can still be removed, and clearing a relation value
drops its links. `CreateEntity`, `ResolveEntity` by name and a non-empty `ListEntities`
filter return `InvalidArgument` for a `structure_type` not in the table. Entities of
such a type written before that check declare nothing, so they take no values.

The frontend fetches the registry once (TanStack Query, `staleTime: Infinity`) and
doesn't render the router until it has loaded, so synchronous code reads it from the
cache via `getStructures()`; components use `useStructures()`/`useStructure()`
(`calcifer/src/model/structures.ts`), and facets the same way via `getFacet()`,
`useFacets()` and `useFacet()`; `propertyDefFor(entity, id)` looks in the entity's
structure, then its attached facets. The frontend keeps only presentation keyed by
type (icon and color, with a fallback for unknown types), presentation keyed by facet id
(icon, nav label and list route: `todo` → check-square, "To-dos", `/v/todos`; an unknown
facet falls back to its plural and no list page) and per-option presentation
such as `PriorityBadge`'s variants (with a fallback variant). Option keys the UI
branches on (status `done`/`open`, priority `none`) stay literal in the code that uses
them. The MCP `list_structures` tool formats the same RPC response.

The entity page (`calcifer/src/routes/e.$id.tsx`) renders a generic editor for every
`PropertyKind`, in the structure's property order, then one section per attached facet
(its name, its properties in order and a "Remove" action that detaches it). "Make a
to-do" appears when the structure accepts `todo` and it isn't attached. A property with
a custom editor skips the generic one: overrides are keyed `Structure.propertyId` for a
structure property (`DailyNote.date`) and by the full id for a facet property
(`todo.status`). Generic editors: richtext → an editor for its document; text and
number → an inline input that writes on blur or Enter (empty clears the value); date →
a date picker; select → a dropdown of its options; relation → a picker for one target;
relations → a list of targets with an "Add" picker. The relation pickers list entities
of `target_structure` (any structure when it's empty) and offer "Create" when the
target has `unique_names`. No structure declares a `text`, `number` or `relation`
property today; they are rendered so one can be added in `structures.rs` alone.

Below the properties, a relationships section
(`calcifer/src/components/relationships/RelationshipsPanel.tsx`) replaces the former
Backlinks panel. It's collapsible, closed by default, headed "Relationships (N)", and
Cmd/Ctrl+Shift+B toggles it. Its rows come from the replica, not an RPC
(`selectRelationshipRows` in `calcifer/src/model/relationships.ts`):

- One row per other entity and direction, each with the reasons it's there. An outgoing
  row (a link the entity holds) reads *related* for a direct relationship and *mentioned*
  for a link from a rich-text document, which includes a `#tag` chip. An incoming row (a
  link another entity holds to this one) reads *related to this*, *mentions this*, or
  *via <label>* for a relation property such as a Note's `tags`, with the property's
  label from the registry, the id if it has none. The entity's own relation-property
  links (`tags`) stay in their property fields, referenced dates aren't listed (they
  belong to the calendar), and a self-link or a link to an entity the replica doesn't
  hold gets no row.
- Order: outgoing rows with *related* first, then incoming rows with it, then the rest;
  within each group the newest link `created_at` first, ties by entity id. After 20 rows
  the rest collapse behind "Show all (N)". With no rows it reads "No relationships."
- Only an outgoing row with *related* has a remove control (`RemoveRelationship`). An
  outgoing row that is only *mentioned* has a jump control instead, since removing a
  mention means editing the author's text: it scrolls to the first mention or hashtag
  chip (`data-type="mention"` or `"hashtag"`, with `data-id` the row's entity id) inside
  `main`, in document order, and rings it for a second. A row with both has the remove
  control only; incoming rows have neither.
- "Add" opens an entity picker limited to the structure's `relates_to` (`useRelatesTo`
  in `model/structures.ts`), excluding the entity itself and what it's already related
  to, and calls `AddRelationship`. It's hidden when `relates_to` is empty. Both writers
  (`useAddRelationship`, `useRemoveRelationship` in `model/store.ts`) update
  `Entity.links` optimistically and roll back on an error.

Current shape:

- **`Note`** — properties: `tags` (relations → `Tag`), `content` (richtext); accepts the
  `todo` facet; `relates_to: Note`. `tags` is what the note is tagged with. A `#tag` in
  its body only references the Tag (the link shows in the Tag's backlinks) and doesn't
  set `tags`. A note is related to another note through a direct relationship, not
  through either's text or properties.
- **`Tag`** — no properties; `mentionable: false` (reached via `#`), a `name` key, so
  `unique_names: true`. `relates_to` is empty: a Tag holds no relationships.
- **`DailyNote`** — properties: `date` (date), `content` (richtext); `creatable: false`,
  `mentionable: false`, `name_editable: false`. The server names it for its date (see
  the DailyNote name rule under RPC surface); the entity page moves a note by setting
  `date` through `DailyNoteDateField`. Uniqueness per day is enforced by its `date`
  key in `entity_keys`. `relates_to` is empty.

Registry tests check that every `relates_to` entry names a structure, and that no
declared property id, of a structure or a facet, starts with `@` (reserved; see Graph
derivation). Widening a `relates_to` list is a registry edit with no migration. Narrowing
one leaves existing relationships that break the new rule; they are kept, and
`RemoveRelationship` still removes them.

**Facets** ([ADR 11](../adr/0011-facets.md)). A facet is a fixed group of properties,
declared in `FACETS` next to the structures, that an entity can have attached or not
when its structure accepts it. It is served in `ListStructuresResponse.facets` and
changed only with a server restart; there are no user-defined facets. A facet declares
properties only: no keys, naming rules or rich text, which belong to the structure. An
entity has at most one of each facet.

- Facet property ids are namespaced and full, `<facet>.<name>`, everywhere: in
  `PropertyDef.id`, the `properties` table, `Entity.properties` and
  `SetEntityPropertyRequest.property_id`. Structure property ids never contain a `.`,
  so the two can't collide. Registry tests enforce this, that no facet declares a
  rich-text property, and that every id in a `StructureDef.facets` names a facet.
- A value on a facet's id is written only while the facet is attached (see
  `AttachFacet` under RPC surface); clearing one is always allowed.
- Values are checked like structure property values, and links derived from a facet
  relation property (none today) use its full id as `source_property_id`.

Today there is one facet:

- **`todo`** ("To-do") — makes an entity actionable. Properties: `todo.status` (select:
  `open`/`done`, default `open`), `todo.priority` (select: `none`/`low`/`medium`/`high`,
  default `none`), `todo.due` (date). Accepted by `Note`. A to-do is any entity with
  this facet; the frontend lists them at `/v/todos`, and the calendar shows each one
  with a `todo.due`. It is unrelated to a task item (a checkbox line in a document).

Adding a select option, or changing a label or default, is a change to
`structures.rs` alone. Adding a Structure is `structures.rs` plus, optionally, an
icon/color entry in the frontend and any custom rendering; a facet likewise, with a
facet presentation entry. No DB migration; the server
must be restarted and clients pick the change up on next load.

## Graph derivation

All of this is recomputed server-side on write; none of it is client-authored. See
[ADR 3](../adr/0003-server-authoritative-link-graph.md). A link comes from one of three
stored sources: a rich-text document's chips, a `relation`/`relations` property value, or a
direct relationship row ([ADR 12](../adr/0012-direct-relationships.md) amends ADR 3 with
the third). Each source owns its own `source_property_id` scope and the server replaces
only that scope when the source changes, so the sources reconcile independently.

- **`Entity.links`** — the full outgoing set, re-derived from document content on every
  save by `extract_doc_references` (`server/src/tiptap/references.rs`) walking the TipTap JSON (see
  [`richtext-doc.md`](richtext-doc.md) for the nodes it reads). Scoped
  per originating property via `source_property_id`, so properties reconcile
  independently.
- Relation properties (`relation`/`relations`) also produce `links` rows, scoped by
  `source_property_id` the same way as richtext-derived links — see
  `sync_relation_links` in `server/src/links/relations.rs`. Server-derived only; no
  client ever authors a link row directly. `CreateEntity`/`SetEntityProperty` return
  `InvalidArgument` if a ref's target isn't the property's declared
  `target_structure`, or if the ref's non-empty `structure_type` isn't the target's
  real type; the link row records the real type. Refs to ids with no entity get no
  link row but aren't rejected. `DeleteEntity` strips the deleted id from other
  entities' `relation`/`relations` values in its transaction (a `relation`, or a
  `relations` left empty, is cleared) and publishes `upserted` for each entity it
  changed. Dead refs stored before this change aren't cleaned up.
- **Relationships** — the `relationships` table is the source and its links are derived:
  after every `AddRelationship` or `RemoveRelationship` that changes a row, the server
  runs `replace_scoped_links` for the source's `@related` scope in the same transaction,
  with every target in the table (real structure type, oldest row first, ties by target
  id). A target that stays keeps its link id and `created_at`. So `links` is still the
  one index that backlinks, the replica and the agent read, and it could be rebuilt from
  documents, property values and relationship rows. Because each scope reconciles alone,
  a rich-text save or a property write never touches `@related` links, and a relationship
  write never touches content links. The same pair can be linked twice, once by a mention
  and once by a relationship; they are two link rows, and removing one leaves the other.
  `Entity.links` stays in `link_id` order, so a link's position says nothing about when it
  was made; read `created_at`.
- **Reserved `@` ids** — property ids beginning with `@` are reserved for the link scopes
  the server derives. `CreateEntity` (a key of `properties`), `SetEntityProperty`,
  `AddRelationTarget`, `RemoveRelationTarget`, `GetRichText` and `PutRichText` return
  `INVALID_ARGUMENT` (`property ids starting with @ are reserved`) for one, before any
  lookup; clearing a value on one is refused too. `ResolveEntity` takes no property ids.
  A property id starting with `@` that was accepted as an ad-hoc id before is now refused.
- **`referenced_dates`** — entity-scoped; the union of date chips across all of the
  entity's richtext documents, recomputed per save.
- **Backlinks** — never stored. Derived by `EntityService.ListBacklinks` from the
  `links` rows whose `target_id` is the entity, one `Backlink` per row; a relationship
  to the entity is one whose `source_property_id` is `@related`. A source linking to
  itself is excluded, on the server and in the frontend's relationships section
  (`calcifer/src/model/relationships.ts`) alike.
- **Deletion** — `DeleteEntity` removes everything the entity owns in one transaction.
  `properties`, `links`, `relationships` (on either end), `referenced_dates`,
  `entity_keys`, `entity_facets`, `richtext` and `chunks` all
  reference `entities(id) ON DELETE CASCADE`. `entity_vec` is a `vec0` virtual table
  keyed by `chunks.id` and can't cascade, so the server deletes the entity's
  embeddings first, while its chunks still name them. Mention chips in other
  documents survive as clickable tombstones; the server sweeps `links WHERE target_id
  = ?` to keep the relational index clean, and strips the id from other entities'
  relation values (see above). A relationship to a deleted target doesn't survive as a
  tombstone: its row and link go, the source's `updated_at` moves, and the source is
  republished (see Watch contract).

## RPC surface

`proto/calcifer/v1/services.proto`. RPCs follow buf's standard naming: each is a verb
and a noun, takes `<Rpc>Request` and returns `<Rpc>Response`, and no message is the
request or response of more than one RPC. A response that carries one entity or
document wraps it (`GetEntityResponse { Entity entity = 1; }`). `pnpm proto:lint`
(in `calcifer/`) checks this.

```proto
service EntityService {
  rpc GetEntity(GetEntityRequest) returns (GetEntityResponse);            // id -> entity
  // Also strips the id from other entities' relation values and drops the
  // relationships to it (see Graph derivation).
  rpc DeleteEntity(DeleteEntityRequest) returns (DeleteEntityResponse);   // id -> {}
  // For the agent; the frontend's replica comes from WatchEntities (ADR 9).
  rpc ListEntities(ListEntitiesRequest) returns (ListEntitiesResponse);  // structure_type filter
  // Create by intent; the server builds the entity. See below.
  rpc CreateEntity(CreateEntityRequest) returns (CreateEntityResponse);  // structure_type, optional name, properties -> entity
  // Only the name; properties are untouched. NOT_FOUND for an unknown id.
  rpc RenameEntity(RenameEntityRequest) returns (RenameEntityResponse);  // id, name -> entity
  // One property of an existing entity; an unset value clears it. Returns the entity.
  rpc SetEntityProperty(SetEntityPropertyRequest) returns (SetEntityPropertyResponse);  // entity_id, property_id, value -> entity
  // A snapshot, then revisioned events; a fresh snapshot after a lag. See below.
  rpc WatchEntities(WatchEntitiesRequest) returns (stream WatchEntitiesResponse);
  // Get-or-create by a name or a day; see below.
  rpc ResolveEntity(ResolveEntityRequest) returns (ResolveEntityResponse);
  // For the agent. One Backlink per link row pointing at entity_id, self-links
  // excluded; newest created_at first, then source id, then link id. NOT_FOUND
  // for an unknown entity_id.
  rpc ListBacklinks(ListBacklinksRequest) returns (ListBacklinksResponse);
  // Attach or detach a facet (ADR 11); see below.
  rpc AttachFacet(AttachFacetRequest) returns (AttachFacetResponse);  // entity_id, facet -> entity
  rpc DetachFacet(DetachFacetRequest) returns (DetachFacetResponse);  // entity_id, facet -> entity
  // Add or remove one target of a `relations` property; see Relations targets below.
  rpc AddRelationTarget(AddRelationTargetRequest) returns (AddRelationTargetResponse);  // entity_id, property_id, target_id -> entity
  rpc RemoveRelationTarget(RemoveRelationTargetRequest) returns (RemoveRelationTargetResponse);  // entity_id, property_id, target_id -> entity
  // Relate an entity to another, or remove that relationship (ADR 12); see Relationships below.
  rpc AddRelationship(AddRelationshipRequest) returns (AddRelationshipResponse);  // entity_id, target_id -> entity
  rpc RemoveRelationship(RemoveRelationshipRequest) returns (RemoveRelationshipResponse);  // entity_id, target_id -> entity
}

message CreateEntityRequest {
  string structure_type = 2;
  optional string name = 3;                    // unset or blank: the server's default name
  map<string, PropertyValue> properties = 4;   // keyed by property id
  repeated string facets = 5;                  // attached on create, with their select defaults
}
message AttachFacetRequest  { string entity_id = 1; string facet = 2; }
message AttachFacetResponse { Entity entity = 1; }
message DetachFacetRequest  { string entity_id = 1; string facet = 2; }
message DetachFacetResponse { Entity entity = 1; }
message AddRelationTargetRequest     { string entity_id = 1; string property_id = 2; string target_id = 3; }
message AddRelationTargetResponse    { Entity entity = 1; }
message RemoveRelationTargetRequest  { string entity_id = 1; string property_id = 2; string target_id = 3; }
message RemoveRelationTargetResponse { Entity entity = 1; }
message AddRelationshipRequest     { string entity_id = 1; string target_id = 2; }
message AddRelationshipResponse    { Entity entity = 1; }
message RemoveRelationshipRequest  { string entity_id = 1; string target_id = 2; }
message RemoveRelationshipResponse { Entity entity = 1; }

message ListBacklinksRequest { string entity_id = 1; }
message Backlink {
  Entity source = 1;                          // the entity whose content/relations/relationships link here
  string source_property_id = 2;              // which property the link came from
```

Property edits go through `SetEntityProperty`, which writes only that property's row and
re-syncs only that property's relation links, so the browser and the agent editing
different properties of one entity don't overwrite each other. Renames go through
`RenameEntity`, which writes only the name (and its FTS row) and `updated_at`, so it can't
undo a concurrent `SetEntityProperty`. `RenameEntity` trims the name and returns `INVALID_ARGUMENT`
for a blank one or one that breaks the name rule (under `CreateEntity`), and
`FAILED_PRECONDITION` for a structure with `name_editable: false` (DailyNote). A
unique-index clash is `ALREADY_EXISTS` with a message for the index that failed: `a Tag named "<name>" already exists` or `a DailyNote for <date> already
exists`. There is no whole-entity write.

`ListEntities` returns entities most recently updated first; entities with the same
`updated_at` come back in `id` order. Within an entity, `links` are in `link_id` order
and `referenced_dates` in date order, whichever RPC returns it.

`CreateEntity` takes intent: `structure_type`, an optional `name` and initial `properties`
(the same `map<string, PropertyValue>`, keyed by property id; an entry whose value has
no case is `INVALID_ARGUMENT`).
The `structure_type` must be in the registry (`INVALID_ARGUMENT`) and `creatable`
(`FAILED_PRECONDITION`, pointing at `ResolveEntity`). The server builds the entity with `new_entity` (minted id and timestamps, select
defaults, then the request's properties laid over them; a request value for a
rich-text property is `INVALID_ARGUMENT`), saves it, publishes `upserted` and returns it. With no name (or a
blank one) the name is `Untitled <StructureDef.name>`, e.g. "Untitled Note"; for a
`unique_names` structure (Tag) the server takes the first free one of `Untitled Tag`,
`Untitled Tag 2`, `Untitled Tag 3`, … (checked against its folded `name` key). A given name is trimmed.
A new entity
has no `referenced_dates`, and its only links are those from relation properties in
the request.

`facets` names the facets to attach on create, each checked as in `AttachFacet`
(`INVALID_ARGUMENT` for one not in the registry, `FAILED_PRECONDITION` for one the
structure doesn't accept). Each one's select defaults are laid under the request's
`properties`. A value on a facet that isn't requested is `FAILED_PRECONDITION`.

**Name rule.** A name can't contain `|` or `]]`, checked after trimming: `CreateEntity`,
`RenameEntity` and `ResolveEntity` by name (when it would create) return `INVALID_ARGUMENT`
with `names can't contain "|" or "]]"`. The agent's link syntax (`[[Name|label]]`, closed by
`]]`) can't express such a name, so a note with one couldn't be linked or round-tripped
through the MCP tools (I-61). A lone `[` or `]` is fine, since only `]]` closes a link.
Existing entities keep any name they already have, and a lookup with `create_if_missing`
unset is an ordinary lookup: it finds whatever has the name, else `NOT_FOUND`.

**Facets.** `AttachFacet` and `DetachFacet` return `NOT_FOUND` for an unknown
`entity_id` and `INVALID_ARGUMENT` for a facet not in the registry. `AttachFacet` is
also `FAILED_PRECONDITION` for a facet the entity's structure doesn't accept. Attaching
inserts the `entity_facets` row and writes the facet's select defaults; detaching
deletes the row, every `<facet>.*` property row and the links derived from the facet's
relation properties. Both run in one transaction, bump `updated_at`, publish `upserted`
and return the entity. Attaching a facet that is already attached, or detaching one
that isn't, returns the entity unchanged with no write and no event. `SetEntityProperty`
of a value on a facet's id while that facet isn't attached is `FAILED_PRECONDITION`
(`attach the todo facet before setting todo.status`); a clear is allowed. There is no
facet argument on `ResolveEntity`: an entity it creates has no facets.

**Relations targets.** `AddRelationTarget` and `RemoveRelationTarget` change one target of
a `relations` property, so two writers adding different targets both keep theirs; two
`SetEntityProperty` calls that each resend the whole list can drop one. `SetEntityProperty`
still writes a whole list (create flows and clears use it), and so does a single `relation`
property, which has nothing to merge and which these RPCs refuse. Add appends the target as
a ref carrying its real structure type; a target already in the list is a no-op. Remove drops
the target; one that isn't in the list, including an id with no entity, is a no-op, and
removing the last target clears the property (its row is deleted). Both run in one
transaction, re-derive that property's links, bump `updated_at`, publish `upserted` and
return the entity; a no-op returns the entity unchanged with no write and no event. Only a
declared `relations` property of the entity's structure or an attached facet is accepted.
Errors: `INVALID_ARGUMENT` for an empty `entity_id`, `property_id` or `target_id`, for a
property that isn't a declared `relations` property (`Note.content is not a relations
property`), and for an Add target whose structure isn't the property's `target_structure`;
`NOT_FOUND` for an unknown entity, and for an Add target that doesn't exist;
`FAILED_PRECONDITION` for a property of a facet that isn't attached. Remove checks neither
the target's existence nor its structure, so a stale ref can always be removed.

**Relationships.** `AddRelationship` and `RemoveRelationship` add or remove one direct
relationship ([ADR 12](../adr/0012-direct-relationships.md)) from `entity_id` to
`target_id`: one `relationships` row, and the source's `@related` links re-derived from the
table, in one transaction. Two writers adding different targets both keep theirs, which
the whole-list `SetEntityProperty` can't promise. A relationship is one-way: B sees A's
relationship to it as a backlink, and nothing is written on B's side. An empty `entity_id`
or `target_id` is `INVALID_ARGUMENT`, checked first. `AddRelationship` then checks, in
this order, and stops at the first failure: the source exists (`NOT_FOUND`); its
structure's `relates_to` isn't empty (`FAILED_PRECONDITION`, `a Tag can't hold
relationships`); the target exists (`NOT_FOUND`); the target isn't the source
(`INVALID_ARGUMENT`, `an entity can't be related to itself`); the target's structure is in
`relates_to` (`INVALID_ARGUMENT`, `a Note can't relate to a Tag`). Only then is a
relationship that already exists a no-op, so the current registry decides whether A may
relate to B, whatever it allowed when the row was written. `RemoveRelationship` checks
only that the source exists (`NOT_FOUND`); it never reads `relates_to`, so a row left by a
narrowed list, even one narrowed to empty, can always be removed, and a missing
relationship or target is a no-op. A change bumps the source's `updated_at`, publishes
`upserted` and returns the source entity; a no-op returns it unchanged with no write and no
event. The row's `created_at` is when it was added.

`ResolveEntity` is the one get-or-create path for both clients (`[[wikilinks]]`, `@`
mentions and `#tags` in the browser; every name lookup and daily note in the MCP
server). The `name` key trims the name and matches it case-insensitively within
`structure_type`, which is required and must be in the registry. For a structure with a
`name` natural key (Tag) the match is on its folded key in `entity_keys`, so it folds
Unicode case. Only Tag names are
unique, so for other structures (matched with the ASCII-only `entities_name_ci` index)
several entities can share a name: the lookup returns
the one with the oldest `created_at`, and the lowest `id` breaks ties, so the same
name always resolves to the same entity. The `date` key takes a canonical ISO day and finds
the DailyNote whose `date` key in `entity_keys` matches. `INVALID_ARGUMENT` for a missing key, an empty
name, an empty or unknown `structure_type` (name), a malformed day, or a `structure_type` other than ""
or `DailyNote` (date). A miss returns `NOT_FOUND` unless `create_if_missing` is set, in
which case the server builds the entity (`new_entity`: minted id, select defaults,
and for a date the `date` property and its name), saves it, publishes `upserted` and returns `created = true`.
Creating by name is `FAILED_PRECONDITION` for a structure that isn't `creatable` (a
DailyNote is resolved by `date`); looking one up by name still works. A miss with
`create_if_missing` set and a name that breaks the name rule (under `CreateEntity`) is
`INVALID_ARGUMENT`.

**DailyNote name rule.** A DailyNote's name is its `date` as a long date ("June 13,
2026"), set by the server when `ResolveEntity` creates it and when `SetEntityProperty` changes its
`date`. `CreateEntity` and `RenameEntity` refuse a DailyNote (`creatable` and `name_editable` are
false). `SetEntityProperty` of
`date` on a DailyNote moves it: it sets the name, the FTS name row and its `date` key
in one transaction, and fails with `ALREADY_EXISTS` if that day already has a DailyNote.
Clearing the date keeps the name it had.

`RichTextService` only addresses declared rich-text properties. Both `GetRichText` and
`PutRichText` return `INVALID_ARGUMENT` for an empty `entity_id` or `property_id`, `NOT_FOUND` if
the entity doesn't exist and `INVALID_ARGUMENT` if the property isn't in its structure's
rich-text properties. `GetRichText` of a declared property with
nothing saved returns an empty `doc` and the epoch as `updated_at`.

`PutRichText` is conditional when `expected_updated_at` is set: clients echo back the
`updated_at` they last read (the epoch if nothing was saved), and a stale expectation
fails with `FAILED_PRECONDITION` and writes nothing. Leaving it unset writes
unconditionally. Each save's `updated_at` is `max(now, previous + 1)` in milliseconds,
so two saves never share a timestamp, and the entity's `updated_at` is set to the same
value in the same transaction. After commit, `PutRichText` publishes `rich_text_changed` with
the saved doc and then `upserted` with the reloaded entity, since its links,
`referenced_dates` and `updated_at` changed.

Transport is gRPC-Web from the browser (`tonic-web` bridges), served under `/api` by the
same process that serves the UI; the Vite dev server proxies `/api` to it.

**Watch contract.** `WatchEntities` is a one-way replication stream of the whole entity set
([ADR 9](../adr/0009-watch-fed-replica.md)); the frontend's replica comes only from it,
and the filtered `ListEntities`, `ListBacklinks` and `Search` are there for the agent.

- The first message on every stream is a `snapshot` of every entity, sent at once
  even when nothing is being written.
- After it come `upserted`, `deleted_id` and `rich_text_changed` events with
  increasing `revision`. The snapshot carries the revision it is current as of, and
  every later event has a higher one.
- Whenever the server can't guarantee continuity (the subscriber fell behind the
  256-event channel), it sends a fresh `snapshot` in place of the missed events, and
  the client must replace its whole set.
- A snapshot doesn't include rich-text docs; clients refetch any doc they hold.
- Revisions restart when the server restarts. Clients never compare revisions across
  streams. There is no resume: a reconnect is a new stream and starts with a snapshot.
- An event after a snapshot may repeat something the snapshot already shows. Applying
  an upsert or a delete is idempotent, so clients apply every event in order.

Every write publishes after its transaction commits: `CreateEntity`, `RenameEntity`,
`SetEntityProperty`, a creating `ResolveEntity` and a changing `AttachFacet`,
`DetachFacet`, `AddRelationTarget`, `RemoveRelationTarget`, `AddRelationship` or
`RemoveRelationship` publish `upserted`, `DeleteEntity` publishes `deleted_id` then one
`upserted` per entity whose relation values it stripped or that held a relationship to
the deleted one (once each, in id order, with `updated_at` bumped), and `PutRichText`
publishes `rich_text_changed` then `upserted`. The
server reads the current revision before loading a snapshot and skips queued events at
or below it, which the snapshot already includes.

## Retrieval

`SearchService.Search` is the RAG substrate; it isn't surfaced in the UI yet. Its
`mode` picks one of three rankings:

- **Lexical** — FTS5 (`entity_fts`, `tokenize='unicode61'`) over entity names plus
  plain text extracted from documents, each query term prefix-matched, ranked by
  `bm25()`. Kept in sync inside the same transactions as `RichTextService.PutRichText` and
  entity create/update/delete. FTS5 can't look up its `entity_id UNINDEXED` column, so
  each entity's row is addressed by rowid: `entity_fts_rowids` maps an entity id to
  its `fts_rowid` (assigned on first write, stable across `VACUUM`, cascading from
  `entities`). A rename updates `name` and a save updates `body` in place. FTS5 rows
  don't cascade, so `DeleteEntity` deletes the entity's row before the entity.
- **Semantic** — vector KNN over chunk embeddings, best chunk per entity. Documents
  are chunked on heading and paragraph boundaries (~500 tokens) into `chunks`;
  embeddings land in a `sqlite-vec` `vec0` table (`entity_vec`) at a dimension pinned
  by the migration, one per chunk, sharing the chunk's `id`. The embed worker replaces
  an entity's chunks off the write path; if the entity is deleted while its docs are
  embedding, the chunk insert fails its foreign key and the worker drops that run.
- **Hybrid** (the default, and what `UNSPECIFIED` means) — the lexical and semantic
  rankings fused by reciprocal-rank fusion.

With embeddings off (the model failed to load), semantic and hybrid behave exactly as
lexical. A hit's `snippet` is plain text from FTS5's `snippet()` around the best
lexical match, and `matches` holds each matched term as a half-open range of UTF-16
code units into it (what JS string indices count). The server marks matches with
private-use code points (U+E000, U+E001) and strips them, so the snippet carries no
markup; a document that contains those characters loses them from its snippet, and
they can shift a match range. A hit only
the vector side found has an empty snippet and no matches.

**Embedder.** A background `tokio` worker drains an embed queue off the write hot
path, behind an `Embedder` trait. Default is local and in-process: `all-MiniLM-L6-v2`
at 384 dimensions via fastembed. No API key; nothing leaves the machine. Changing the
model requires a re-embed and a migration.

## MCP tools

`server/src/mcp/` hosts the MCP server inside the backend, as streamable HTTP at `POST /mcp` on its own listener (`CALCIFER_MCP_ADDR`, default `127.0.0.1:8081`)
(JSON replies only; no server-initiated stream). Its tools call the services in-process.
Because it has no auth (ADR 5), `server/src/security/local.rs` refuses requests a web page
could forge: a `Host` that isn't this machine (403, against DNS rebinding), an `Origin`
that isn't loopback (403), and a POST body that isn't `application/json` (415, so a
cross-site `no-cors` `text/plain` POST can't run a tool). Agents like Claude Code send no
`Origin`; browser tools on `localhost`, such as the MCP Inspector, pass.
It exposes thirteen tools:

`search_notes` · `get_note` · `query_text_location` · `edit_note` · `create_note` ·
`append_to_note` · `tag_entity` · `link_notes` · `unlink_notes` · `get_backlinks` ·
`create_daily_note` · `append_to_daily_note` · `list_structures`

`search_notes` makes one `Search` call in its `mode` (default hybrid) and writes each
hit's snippet with its matches in `**bold**`, so they never read as wikilinks.

`get_note`, `query_text_location` and `edit_note` take exactly one of `name` (a Note) or
`date` (a DailyNote, `yyyy-MM-dd`); both or neither is a tool error. A date is looked up
with `ResolveEntity` by date and never created: a missing day is an error that points at
`append_to_daily_note`, and a malformed one fails with the server's `INVALID_ARGUMENT`
message. They read and write the body of whichever they find, and their messages name it by
kind: `Note "X"` or `Daily note "October 24, 2026"`. `append_to_note`, `tag_entity` and
`get_backlinks` stay Note-only, by name; `link_notes` and `unlink_notes` are Note-only, by
name or id.

`get_note` returns the note's markdown under a frontmatter block of `name`, `version`,
`tags` and `related`, each a JSON value on its own line. `tags` is the names of the note's
Tags in the property's stored order, `[]` when it has none; a ref whose Tag no longer
exists is skipped. `related` is the names of the notes it holds direct relationships to,
oldest first by the link's `created_at` (ties by target id), `[]` when it has none; change
it with `link_notes` and `unlink_notes`. `create_note` ignores a `related:` line, so a
`get_note` result copied into `create_note` keeps its tags but relates the copy to nothing.
A daily note's block is `name`, `version` and `date` (the ISO day) and neither `tags` nor
`related`, since only Notes have them.

`link_notes(from, to)` relates one note to another through `AddRelationship` and writes no
text into either; `unlink_notes(from, to)` removes that relationship through
`RemoveRelationship`. Each argument is a note's name or id, and nothing is created: a
value that parses as a UUID and names an existing Note is used as an id; otherwise it's
matched against every Note's name, case-insensitively with the registry's Unicode
folding. No match is a tool error, pointing at `search_notes`. Several matches is a tool
error listing each as `- name (id)`, since Notes have no name key (ADR 11); the agent calls
again with the id. `from` is resolved first, so its error is the one reported, and the
server's own errors (a note related to itself, say) come through. The result is `Related
"A" -> "B".` or, when it already was, `"A" was already related to "B".`; `unlink_notes`
says `Unrelated "A" -> "B".` or `"A" wasn't related to "B".`. A relationship is one-way,
so `link_notes("A", "B")` shows in A's `related` and in B's `get_backlinks`, not in B's
`related`. A `[[wikilink]]` in a note's text isn't a relationship, and `unlink_notes`
doesn't remove it.

`get_backlinks` lists each source note once, however many links it has. A source with a
direct relationship to the note is labelled `(related)`; one that links from a
non-rich-text property is labelled `via <property ids>`, and one with both
`(related, via tags)`. A source that links only from its documents is bare.

`list_structures` formats the structure registry (`structures.rs`): each structure's type,
description, properties (kinds, select options and defaults, relation targets), the
facets it accepts (`facets: todo`) and, when it has any, the structures it may relate to
(`relates_to: Note`), then each facet as `- facet todo (To-do):
<description>` with its properties and the structures that accept it (`accepted by:
Note`). No tool attaches or detaches a facet.

Writes go through the same service methods the browser's RPCs reach. Markdown is converted
to TipTap JSON in `server/src/mcp/markdown.rs`, resolving `[[wikilink]]` and `#tag` through
`ResolveEntity` by name. A missing `#tag` is created; a `[[wikilink]]` to a missing target
fails the call, which writes nothing. A body `#tag` only references its Tag; it doesn't
tag the note. `create_note` fails for a name that already exists or breaks the name rule (a `|` or
`]]`), and takes an optional
`tags` list: each name is resolved or created as a Tag (repeats folded) and set as the
note's `tags` property through `SetEntityProperty`, after the body is written. Without a
`tags` argument it takes the `tags:` line of the markdown's leading frontmatter, a JSON list
of strings, so a `get_note` result copied into `create_note` keeps its tags; a value that
isn't one fails the call and writes nothing. A `tags` argument, even an empty list, wins over
the frontmatter. Its result counts the body's links (`Wikilinks: N`) apart from the `tags`
links (`tags: N`).

`tag_entity(name, add, remove)` tags or untags an existing note, found by name as
`append_to_note` finds it and never created. Only Notes have `tags` today (ADR 11).
`add` and `remove` are lists of tag names, each optional, but one must be non-empty; a name
in both lists (compared case-insensitively) fails the call and writes nothing. Each `add`
name is resolved or created as a Tag (repeats folded) and added with `AddRelationTarget`;
each `remove` name is looked up without creating, a Tag that doesn't exist or that the note
doesn't have is skipped, and the rest go through `RemoveRelationTarget`. A tag someone else
adds meanwhile is kept. The result names the note and its tags afterwards,
`Tags on "X": ml, papers.` (`none` when it has none).

`create_daily_note` and `append_to_daily_note` get-or-create the
day's note with `ResolveEntity` by date; `create_daily_note` says whether it was created or
already existed. An agent creates a note with wikilinks, the server derives the graph,
and open browser tabs update live over `WatchEntities`.
